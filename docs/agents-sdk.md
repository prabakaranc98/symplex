# OpenAI Agents SDK integration

Symplex uses the official `openai-agents` Python package for proposal specialists. Each `OpenAIProvider.propose` invocation creates a named SDK `Agent`, exposes the strict `submit_proposal` function tool, and executes the real SDK `Runner`. The tool returns the model's proposal to the host. Successful tool execution is not scientific validation or permission to execute the proposal.

The SDK `BudgetedProposalModel` delegates its sole model request to the existing `OpenAIProvider._call` gateway and returns the native Responses result to the host. That gateway chooses the explicitly configured role model, reserves persistent global and scoped budgets, records the raw response, and settles reported usage. The adapter has no separate API client or billing ledger. Unknown usage retains its reservation; actual overruns remain charged and prevent future admission. The installed version is locked in `uv.lock` and `requirements.lock`.

Each specialist run allows one model turn, disables SDK model retries, and stops at `submit_proposal`. A second request is also rejected by the custom Model itself. Full contract parsing and at most one bounded correction remain in the host provider; any correction is another separately budgeted SDK run. Incomplete Responses fail in the existing gateway after preserving the response and usage, before the SDK can treat partial arguments as an accepted proposal.

`sdk_agent_run_started` and `sdk_agent_run` artifacts record the specialist, SDK version, configured model, scope, context digest, response ID, tool invocation count, and outcome. They omit prompts, proposal arguments, exception text and credentials. SDK external tracing is disabled explicitly, including when a caller has an enabled enclosing trace. Existing local `model_response`, `model_call`, and failure records remain the accounting evidence.

The scientific controller still owns investigation state, dataset acquisition, code execution, comparisons, critique, permissions, human steering and evolution. Those tools have not been converted into SDK handoffs or agents-as-tools. `invoke_proposal_async` supports independent concurrent specialist calls through their existing scopes; the synchronous provider uses `invoke_proposal`. Calling that synchronous entry point inside an active event loop fails before starting a request.

Future migration can move independent read-only specialist batches to SDK agent tools after dependency and permission checks, then map host checkpoints to SDK resumable state. That requires preserving the existing scoped reservations, evidence lineage and steering boundaries. SDK adoption alone does not establish better scientific answers or workflow performance.

Validation includes real SDK Agent/Runner tests using the native OpenAI client with a mocked HTTP transport. Those tests establish the adapter and accounting behavior. They do not establish a completed live scientific workflow; live campaign outcomes are reported separately in the [campaign audit](live-campaign-audit.md).

Implementation checked against the official [Agents SDK guide](https://developers.openai.com/api/docs/guides/agents/sdk), [Python SDK repository](https://github.com/openai/openai-agents-python), [models and providers guide](https://developers.openai.com/api/docs/guides/agents/models), [running agents guide](https://developers.openai.com/api/docs/guides/agents/running-agents), and [tracing guidance](https://developers.openai.com/api/docs/guides/agents/integrations-observability) on 2026-09-10. The current [model guidance](https://developers.openai.com/api/docs/guides/latest-model) identifies `gpt-6-astra`; existing explicit role routing is retained.

Live verification on 2026-09-10: Hudson produced seven native Responses through the SDK specialist runner, including two ExperimentProtocol proposals ([sdk_agent_run_e9f0746b27d94dbb](../.symplex-campaign/artifacts/4ddc2b56dc09c49cc92709fa054e1e889c2cd1a29f29828745ce9549b441fe33.json), [sdk_agent_run_e44e48821e244c98](../.symplex-campaign/artifacts/f19d28c80ddbc8ac0da0a498f7804ba91950f2b79a0b923c5363115af3dcd7ae.json)). Both protocol proposals were rejected by host validation; a later protocol request was denied before execution because its scope reservation would not fit. This establishes live SDK transport/tool invocation and budget enforcement, not a completed scientific workflow. Earlier network-context failures retained their unknown-usage reservations.
